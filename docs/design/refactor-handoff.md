## 2. 已确定的方向

- 可信内部团队，管理员开通成员，默认无公开注册。
- 成员可配置自己的模型地址和 Key；平台公共模型及团队分配在 P5 加入。
- LangChain/LangGraph，模块化单体，API/Worker 分进程，PostgreSQL 与 Redis 保存共享状态。
- P1 仅基础文本对话；P2 图片、P3 MCP/Tool、P4 子智能体、P5 团队应用与外部图文 API。开放 API 与后台完整对话查询同步交付。
- 新工程固定放 `platform/`，旧 `BE/`、`FE/my-chat-app/` 独立运行，P1 不切官网流量。
- P1 的默认值已写入实施方案，日常实现细节按该方案处理，不重复询问已确定的产品方向。

## 5. 工作区保护与交付

开始工作先执行 `git status --short`，读取现有差异，记录基线。当前 BE、FE、README 和旧图均存在既有修改；不要 reset、clean、覆盖或整目录格式化这些文件。没有被要求时，不把旧代码全部迁移进新目录，不提交无关更改。

本次交接必须携带以下文件：

```text
README.md
docs/design/2026-10-31-ai-platform-refactor.md
docs/design/2026-11-02-p1-implementation.md
docs/design/refactor-handoff.md
docs/diagrams/README.md
docs/diagrams/refactor-target.mmd
```

同一个工作区可直接读取这些文件。新会话若使用新的 clone，必须读取包含它们的提交；Git 暂存不等于提交，更不等于已推送。本轮可将新增设计文件纳入暂存，但不自动提交/推送，也不把已有 README 修改全部暂存。交付者提交时需精确检查这些路径的 diff；只复制文档也可交接规划，但实现仍需要对应源码基线。

设计文档中的未来 platform 路径是目标目录，不是坏链接或缺失的现有实现。不得为了让清单看起来完整而创建无功能占位文件或把未来命令标记为已成功运行。
